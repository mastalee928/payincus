# 一机一卖五轮审视（本机，2026-11-10）

本轮围绕“一台宿主只卖给一位客户”，检查非特权加固后的空闲可售、已有客户保护、开通、重装及删除回池。此前通用实例、克隆、普通公网地址池修复保留并另见[前阶段收尾](instance-lifecycle-review-2026-11-10.md)，不能把这些旁支的通过结果当成本轮独占交付验收。

基线为 `2620f05ba44a7ffd23bb9a3fe84a73aecb7109c4`，分支 `codex/automatic-hardening-grub`，实际源码包含未提交修改，由 `logs/pool44-evidence-index.json` 保存文件 SHA256。没有连接主控、真实宿主或客户，没有部署、提交、推送或发行。`.taste-skill/` 和前阶段文件保留。

## 第一轮：宿主系统、架构与首次／重新接入

检查 `hostOnboardingWorker`、目标系统探测、安装会话、`routes/hosts.ts` 和管理通道修复。AMD64/ARM64 按实际目标架构判定；未建立正式宿主身份的接入失败重试与已建立原身份的管理恢复分开。保留原租约、当前管理员权限、当前系统和证书检查。

本轮修复：有客户占用，或虽已标记删除但尚有清理／账务／重装／换机残留的独占宿主，不能再次生成完整安装会话或下载完整安装器；维护中同样拒绝。重新生成会话在宿主行锁内检查，拒绝不改原安装令牌、安装状态与 TLS 身份。原管理通道故障继续走 `host-management-repair`，不能用重装宿主恢复管理连接。

证据：两架构安装会话专项、接入租约、当前系统、管理通道修复、安装脚本与输入守卫均通过。测试为本机 PG／协议替身；未对真实宿主执行重新接入、DD、系统安装。下载入口的即时门禁无法撤回已下载到机器上的旧脚本，不能称全部执行时竞态已消除。

## 第二轮：非特权加固、周期复查与原客户恢复

检查 `security-hardening-queue`、`host-security-maintenance`、`customer-boot-recovery`、回执与库存就绪条件。保留前轮安全回退后的重新验收、旧失败预算不覆盖新成功、当前身份及未结束维护保护。

本轮修复：已经付款且正在开通的实例占住宿主时，周期加固不先覆盖它的有效回执再等待开通；保存原回执和到期时间，交付／清理结束后自然复查。开通开始时取得的同一完整回执仅因镜像下载期间到期，不使健康交付失败；防护内容、身份、安装／维护状态有变化仍拒绝，Agent 新鲜度仍按当前时间检查。该有效时点是开始开通，不是更早的扣款时间；长时间排队至开始前已过期仍会走失败补偿。

已有客户的故障恢复增加原登记 UUID、已有创建时间、container 类型、系统盘归属，以及存在时的 owner 标记检查；不以同名为身份凭据。恢复操作在锁内再核当前管理员与账户状态。有客户恢复仍保持已占用，不能变成库存。

兼容性回归曾发现新增身份检查挡住旧版失败换机源恢复；已保留该专用恢复原有的原宿主 pin、成功交付时间界限、重复 UUID 与网络核验流程。仅该明确的旧源恢复分支可继续，普通库存恢复不能据同名放行。

证据：真实 PG 队列、客户恢复、维护和恢复期限专项通过；旧失败换机恢复回归通过。原生启动维护白名单仍仅 `alpine-apparmor-grub-v1:x86_64`。ARM64 已具备防护的库存流程、4K／16K／64K 页大小探测覆盖，不等于 ARM64 内核引导和真实重启验收。

## 第三轮：库存、锁内下单与不重复出售

检查 `pool-stock`、`host-pool-prices`、`host-inventory`、`host-resource-usage`、宿主分配器及真实 `pool-orders` 下单入口。

本轮修复：公开目录、管理员库存与分配器统一计算未结束创建／重装任务对源、目标宿主的占用。批量读取任务，一次合并宿主集合，避免每台单独查询。即使客户记录已 deleted，FAILED 任务的 `cleanup_pending` 仍保留库存；核验完成变为 `cleaned` 后自然恢复，不删除历史回执。

证据：AMD64 E2／ARM64 ARM2C 的实际加固队列→四类库存入口→锁内分配验证；已有／新接入、回执异常、维护和残留保护通过。真实 PG 下单专项覆盖并发预占、整单回滚、重复请求、跨用户、当前权限撤销、价格与退款；账务不因重复请求重复扣款。其 Incus 连接失败是注入的交付失败用例，不是成功开机证据。

## 第四轮：独占开通、客户系统、重装与全端口

检查实际 `pool-orders.startProvisioning`→`createInstanceAsync`→`pool-provisioning`→`dedicated-delivery`；客户重装沿 `instanceTaskWorker` 与持久重装身份；全端口走专属地址转发及宿主 IPv6 同步。

本轮修复：开通结束前核原尝试标记、完整 UUID、有效且未变化的创建时间、default 项目、container、非特权配置／profiles 和真实运行状态；最后在实例／宿主锁内复核原管理身份、架构、当前防护和专属地址，再落 running。最终核验只读，不把数据库显示 running 当作远端已运行。

本轮还修复机器池 IPv6 地址“先查重再写入”的并发窗口：使用共享地址事务锁，等待后重查当前占用，冲突最多尝试 20 次；失败回滚，原有预留复用。针对真实 `startProvisioning`，用同子网两宿主竞争强制碰撞验证，覆盖两架构各三场景；未引入第二种公网交付模式。

证据：28 个双架构开通终态场景（各 14）及现有失败补偿专项通过；专属全端口地址转发的归属、幂等和用户视图专项通过，转发采用整个地址且不生成客户手动端口表单。18 个系统／版本别名×container／VM 的密码配置及回环 SSH 原密码、主机身份、错误密码拒绝检查通过。前阶段通用重装 78 场景另列复核证据，不代替一机一卖完整重装验收。

仍未完成：`dedicatedIpv4=true` 的完整原生开通／重装→客户真实 SSH→公网全部 TCP／UDP 的端到端流程，以及各 Linux 系统、ARM64 原内核运行。本机协议替身、配置检查与真实公网转发分别计证据；既有换机测试中关闭 dedicatedIpv4 的成功分支不能用于声明完整独占交付成功。

## 第五轮：到期、失败清理、账务保持及回池

检查 `instance-deletion`、`host-pool-cleanup`、恢复队列、重装中断协调器与续费恢复。远端实例、磁盘／快照和转发没有确认清理前，仍保留隔离及库存；退款、删除与资源释放维持原有幂等关系。

本轮复现并修复：旧重装任务即使显示 FAILED，只要未交付残留尚未清理，删除入口仍需等待，不能先把客户记录改为 deleted，反过来让原清理协调器永远拒绝。现删除事务纳入未完成创建回执；被拒绝时实例状态不变。原清理核验完成后，下一次删除可正常受理。

证据：双架构真实重装 worker 制造残留→删除拒绝且整行未变→原协调器清理→删除受理通过。管理员真实 TLS 删除矩阵、退款／不退款、并发请求、权限和失败保护通过；回池专项核原清理 done 后再次隔离时的新检查、不重放旧删除、未知磁盘仍保留，以及扫描／重试竞争。自动补续专项保持原账期、实际恢复与一次扣款。没有调整生产账单、余额、续费意愿或客户状态。
