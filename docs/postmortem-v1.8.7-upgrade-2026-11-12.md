# v1.8.7 升级回滚事故复盘与防复发门槛

记录日期：2026-11-12（北京时间）。Owner要求保留这次教训，后续修改安装、OTA、签名组件或发行流程时必须查阅。修复版本为v1.8.8；[发行证据](release-v1.8.8-validation.md)记录源码、Actions及公开资产，本文记录失败机制与今后必须保留的验证。

## 发生了什么

2026-11-12 12:34:01，主控任务33从v1.8.6升级v1.8.7。ARM64发行包下载和SHA256验证成功，新增`20261111170000_instance_renewal_price`迁移成功。随后新包的`install-platform-backup.sh`调用网关组件登记刷新，在`existing-identity`阶段返回`GATEWAY_CONTROLLER_PROVISIONING_REJECTED`。12:35:51代码自动回滚完成。

事后只读核验确认：主控运行v1.8.6，唯一后端健康；原平台身份、签名密钥、公钥信任、组件内容hash、属主和权限正确。数据库新增nullable续费价字段仍在，13个实例均无override。该次取证没有修改生产配置、数据库、身份或客户；后续未代执行v1.8.8生产OTA，不能把以下隔离验收当作主控已升级。

## 根因与漏检

1. **把当前文件清单套给历史已登记组件。** v1.8.7新增`ensure-time-sync.py`，固定签名组件清单由20项变21项。刷新登记前，新验证器先核旧组件，却要求旧v1.8.6也存在新增脚本。原包完整且签名正确仍被拒绝。`existing-identity`只是失败阶段，不能直接解读为身份损坏。
2. **首装覆盖不了真实旧版升级。** v1.8.7的CI、双架构首装、备份恢复和实际发行包核验都通过，但没有运行原v1.8.6包内worker升级到候选包。首装初始化的是新组件，遇不到旧20项登记。测试数量、三轮审视和打包成功都未补上这一场景；此前据此完成发行，是这次漏检的流程责任。
3. **升级兼容必须同时考虑回退。** 修复过程中进一步发现：若新21项组件已经登记，后面的生产就绪检查再失败，切回旧代码后，旧验证器会反过来拒绝新登记。此项为复查发现并在隔离故障注入中验证的关联缺陷，不是任务33日志中的实际失败点。
4. **代码回滚不会撤销已成功的数据库迁移。** 不能把回滚后的机器当成未经升级的干净v1.8.6；再次升级须兼容迁移已执行、字段已存在，保护原数据，不重复添加或自动恢复旧数据库覆盖新账目。
5. **包内有修复，不等于当前进程已运行修复。** 主控／宿主约14秒偏差相关的签名心跳归一化、固定Incus响应Date判断、校时助手及旧worker安装钩子均在两个v1.8.7公开包内，并非漏包。升级回滚后主控仍运行旧逻辑，不能以“包里有”宣布线上不再反复不可售。

## 已落地的修复

- 已登记旧版本按精确历史清单验证，保留原pin、签名、版本、完整sourceCommit、协议、文件hash／大小／权限／属主及路径检查。新包、新安装和普通refresh仍要求完整新清单。不得接受缺文件、额外文件、链接、篡改或新版本伪装旧清单。
- 新包通过原旧worker已经调用的`install-platform-backup.sh`安装校时与兼容工具。只修改新worker不能修复第一次从旧版升级时的执行路径。
- 固定root目录保存新版组件验证工具；旧worker切回当前运行目录后，已有harden回调按原信任核对该发行包并同步组件登记。限定当前runtime入口，保留平台／WireGuard／管理SSH身份，不以重新初始化密钥修复升级。
- `check-release-runtime-files.py`在两个架构打包后对实际tar逐文件比对前端、后端、迁移、模板、运行脚本及双组件校时入口，缺失、混入旧内容、错误属主均阻止发行。该校验不替代独立签名验证和实际升级。

## 后续发版必须保留的门槛

| 验证 | 必须使用的输入与通过证据 |
|---|---|
| 正常旧版升级 | 从已公开且校验通过的旧包安装，运行其中原worker升级到本次完整候选包；核任务成功、唯一健康后端、身份和组件登记、安装钩子实际落地 |
| 已迁移后回滚状态 | 保留旧代码及原子current布局，实际执行候选迁移后再升级；核迁移记录恰一次、数据保持、版本与登记正确 |
| 后半程失败回退再升级 | 新组件已安装登记后注入一次生产检查失败；核旧worker实际回滚、旧后端健康、旧组件登记和原身份保持，再次升级成功 |
| 新装与架构 | AMD64和ARM64分别执行首装及上述三场景，共两条首装和六条旧升级；一个架构成功不能替代另一个 |
| 实际包与线上效果 | 实际tar内容、签名、hash、API digest／size和OTA清单一致；另外记录目标主控运行版本、校时实际状态和宿主回执，不能用Release成功代替生产观察 |

这些场景已由`.github/workflows/release.yml`的`legacy-upgrade`与`fresh-install`约束正式Release依赖。将来支持的升级起点或组件格式变化时，应按兼容承诺更新／扩展输入；仅永久保留v1.8.6这一固定样例，不能证明未来所有旧版本兼容。检查具体来源及所有job终态，不删除、跳过失败场景或无依据重跑相同输入。

本次候选HTTP元数据和下载由本地候选tar提供，其余原worker、PG、迁移、文件系统、systemd、HTTPS前端及生产就绪检查真实运行。故障回退场景只注入一次生产检查失败，其余升级和回滚执行实际路径。它验证旧worker执行兼容，不冒充生产网络下载或生产主控OTA。

## 同轮测试环境教训

- 初次回滚状态预览在**旧环境准备重启**时失败，尚未执行升级：复制`.env`保留了模式却没有保留group。补实际installer的seal／属主整理后通过。必须记录失败阶段并保存脱敏服务日志，不能把测试环境缺陷写成生产新根因，也不能放宽文件权限验证。
- 本地Alpine用BusyBox `cp`运行GNU模式保留测试失败；补齐GNU coreutils后原测试通过。原生依赖、权限和systemd证据需真实环境，Windows语法检查不能替代。
- 状态写`scheduled`只表示校时任务已安排；需回读新鲜的`synchronizing`／`synchronized`状态。时钟容差不能放宽过期回执、重放或实际网络防护检查。

## 防止错误处置

出现相似升级拒绝时，先分清包清单演进、真实签名／身份损坏、权限问题和执行阶段；保留原身份，不删除登记重新初始化，不从包中自行接受新公钥，不跳过DB／支付就绪检查。先完成已授权只读取证，从源码修复并通过上述场景后发行。代码回滚和数据库状态分别核对；不自动恢复旧库以掩盖迁移问题。
