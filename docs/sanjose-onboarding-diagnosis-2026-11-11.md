# 圣何塞两台宿主接入耗时、加固与可售波动检查报告

2026-11-11。范围：sanjose-amd-3、sanjose-amd-4，从本次 SSH 对接到一机一卖可售。本文是实际诊断和下一版维修清单，尚未实施本批产品修复。

**结论：前面未通过的直接原因是两台初始未启用 AppArmor。程序后来自动完成依赖安装、引导配置、一次维护重启和验收。耗时被全局串行维护及重复等待拉长，页面又未展示真实阶段。此外，主控没有持续校时，已实测造成成功后的可售状态短暂波动，仍须修复。**

- 两台 Agent 都是 v1.0.6，Alpine 3.24.3、x86_64、内核 6.18.60-0-virt；原 SSH pin 认证通过。当前无客户实例、预订或运行中实例任务。
- 两台 AppArmor 实际启用，SSH 安全检查通过，已安装 OpenSSH 10.3_p1-r2。远端原维护 journal 均为 `customers-restored`，依赖阶段为 `verified`，新 boot ID 与原记录不同。各有一个维护请求及一次 reboot-intent；没有证据表明重启了 8 次或 15 次。

## 3. 前面为什么不通过，为什么反复“尝试”

**初始真正不通过的是 AppArmor。** 两台首次持久日志均明确“宿主未启用 AppArmor”。原引导备份没有启用参数，维护前 AppArmor 不在启动级别；原维护计划为两台各补齐 6 个官方 AppArmor 依赖包，保留原版本基线后配置启动和重启。当前回执已验证完成。这是纯净 Alpine 接入需要自动完成的步骤，不能要求管理员预先手工准备。

**amd-4 额外等待来自全局维护串行。** `host-security-maintenance.ts` 会检查全库非终态维护；只要另一台尚在维护，就抛出 `HARDENING_BATCH_PAUSED`。当时只有这两台有该时间窗内的维护请求，amd-3 从 11:00:55 维护至 11:04:45，amd-4 到 11:05:08 才开始自己的维护。

amd-4 从首个不通过到进入维护约 **3 分 55 秒**。期间 11:01:12、11:01:53、11:02:32、11:03:11、11:03:49、11:04:29、11:05:08 共记录 7 次 AppArmor 未启用。代码把批量等待写为 30 秒后检查；接入下轮又先完整检查，再尝试领取维护，所以约每 39–41 秒得到相同结论。前台领取次数因此持续增长。

全局限制作业是为避免多台同时重启造成影响，但**等待其它机器时反复重查自身，既浪费时间和资源，又没有向管理员解释排队原因**。扩大规模后不能简单用更多重试掩盖这个问题。

## 4. 单台准备阶段为什么也慢

amd-3 从准备到重启意图约 **139 秒**，amd-4 约 **132 秒**。

远端维护模板分开执行：依赖模拟并保存精确计划 → 安装依赖 → 编译验证策略 → 修改引导并最终检查。前三步成功都返回 `preparing`；主控每次均固定设置 **30 秒后续接**。因此本次缺依赖路径至少有 **3 × 30 = 90 秒** 的人为等待，再加命令、连接和 worker 调度耗时。

分步执行和持久回执有必要：它们防止超时后重复安装、跨越租约或误重启。应调整的是“成功完成一步仍按失败等待 30 秒”的调度，保留每步独立预算、原请求和写前复核。

两台在重启后各记录一次 `HARDENING_REMOTE_RESULT_UNKNOWN`，随后按原身份恢复并通过。它只证明该次未取得可用远端结果；现有日志不能再细分为 SSH 握手、命令超时或哪项网络异常，不应编造具体原因。

## 5. 新发现：主控时间不同步让可售反复变化

这是仍存在的实际问题，优先处理。

- 主控：`NTP=no`、`NTPSynchronized=no`；检查的 systemd-timesyncd、chrony、ntpsec 均 inactive。
- 两台宿主：chrony 正常同步，偏差低于毫秒级；经受信 SSH 比较时间，宿主比主控快约 **13.4–14.4 秒**。
- Agent 请求认证允许 5 分钟时差，所以心跳仍可成功；防护回执却只允许 `checkedAt` 领先主控 **5 秒**。新心跳带来的健康回执会在一小段时间内被判为“来自未来”。

实测连续快照（北京时间，均保持 Agent 在线、`applied=true`）：

| 采样时刻 | 宿主 | 回执相对主控 | 防护门槛／库存查询 |
|---|---|---:|---|
| 11:21:56 | 两台 | 已在过去 | 两台通过 |
| 11:22:06 | amd-4 | 领先约 9.18 秒 | **两项均不通过** |
| 11:22:16 | amd-3 | 领先约 5.15 秒 | **两项均不通过** |
| 11:22:16 | amd-4 | 已在过去 | 恢复通过 |
| 11:22:26 | 两台 | 已在过去 | 两台恢复通过 |

因此“接入成功”之后，真实库存仍可能短暂消失。相同回执检查也用于接入最终门禁，会造成额外等待；但历史每轮门禁失败细项没有保存，**不能把历史第 1–14 次全部归因于时差，也不能断言第 15 次恰好是哪项时钟阈值变化**。

这类判断用于所有依赖该回执的宿主，不限圣何塞两台；此次只对这两台实测，未全量扫描其他机器或客户。

## 6. 为什么页面看不出真因，先前测试为什么没发现

- `finishSecureOnboarding()` 将防护回执、心跳、维护、安装、身份及完整安全状态等多种不满足条件统一报 `HARDENING_ONBOARDING_PENDING`。
- 接入 API 不返回维护子阶段、依赖进度或阻挡它的维护目标；页面主要显示大阶段、总领取次数和最后一个错误码。
- 成功时清除最后错误码；缺少每轮门禁失败条件、等待原因和耗时的结构化历史，无法逐次重建全部 15 次过程。
- 现有维护测试验证“另一台维护时拒绝进入”和“依赖分步返回”，接入测试常主动把 nextCheckAt 调到已到期以验证续接；覆盖正确性，**没有验证两台纯净宿主真实墙钟耗时、排队重复探测次数及主控慢 14 秒时完整可售周期**。
- 已有 CI 和双架构发行证据保留，不能将其视为本次纯净宿主接入体验已验收。

旧主控在线纠偏默认**平滑校正**，不执行无条件 `date -s`／大幅跳时，不改账期、付款时间或客户记录；严重偏差要有独立处理策略和清楚状态。校时与当地时区是两件事，保留用户既有时区，UTC 业务时间不随显示时区改变。校时进程应常驻低开销，不在每次请求中启动安装或探测。

升级接入必须使用**旧 v1.8.6 已会调用的新包安装钩子**。只在新版更新 worker 中新增调用，旧版升级这一轮未必会执行到。已定位旧 worker 调用新包 `scripts/install-platform-backup.sh`，以及新装与后台启动使用的 root 受信助手；实现时应通过该受信链安装独立校时维护组件，并验证回退、重复执行与恢复保护，不能新增任意 root 命令入口。外部网关相关新增文件也须进入原受信签名组件包。

主要涉及文件：

- `scripts/install-panel.sh`、受信升级安装钩子、`scripts/setup-onboarding-control.py`／`install-onboarding-gateway.sh` 和外部网关安装器：自动校时入口。
- `server/src/lib/guest-network-protection.ts`、`server/src/routes/agent.ts`、`server/src/lib/host-resource-usage.ts`：回执与库存时间语义。
- `server/src/services/host-security-maintenance.ts`、`server/templates/host-security-maintenance.py`、`server/src/workers/hostOnboardingWorker.ts`：排队、分步续接与次数。
- `server/src/services/onboarding-security-gate.ts`、接入 API、管理接入页面：具体阻断、历史和进度。
