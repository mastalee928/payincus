# 实例备份恢复后续施工复审

2026-10-28。此文保留原代码审查基线与后续规格；实际已实现部分见下方和HANDOFF。平台OSS恢复与客机磁盘恢复是不同流程。

## 已实现的第一阶段

入队/领取/执行准备已增加current actor/session、独立owner、原host/instance/backup摘要和ready备份核验；host队列上限同锁、其它工作流门禁、UUID临时名和attempt CAS、取消当前权限复核。准备失败零远端补偿，未开始的FAILED不允许rollback。14种变化/3个边界和PG/Fastify/mTLS拒绝专项通过；不等于下列远端步骤已经闭合。

后续优先补远端原UUID/设备清单及临时副本完整性。stop异常吞掉已在第二小段移除，查询/停止/确认共用90秒截止，未知状态与仍Running拒绝；导入前失败不清理临时副本、不执行副本rollback，实际mTLS及worker专项通过。执行前事务之后、connect/流量补采期间仍有变更窗口；补采helper还会重新查询host，必须结合持久阶段修复，不能把单次摘要检查解释成整个操作期授权锁定。成功末尾清理DB和副本、失败/启动/超时、真正rollback仍沿用旧主逻辑；未知状态持续门禁与唯一副本保护尚未完成。

## 后续新增网络复审

当前恢复删除旧原实例调用普通`incus-instances.deleteInstance`，该helper随后`removeDedicatedForward(client, name)`，会删除description为`payincus-dedicated:<原名>`的全部IPv4/IPv6网络forward。恢复主流程未重新配置这些规则，可能恢复磁盘后丢失客户公网连接。下阶段应在固定原设备、UUID、双栈目标地址、临时副本和池身份确认后，使用恢复专用的精确实例删除/缺失确认路径保留网络forward，并在重命名后核对原地址/设备及规则；不能仅改删API就声明双栈已验。临时清理同样不得误触原名绑定规则。普通客户销毁仍须原有转发清理和库存保护。

## 施工前缺口基线（已实现部分以顶部为准）

- `db/restore-tasks.ts`入队只锁instance并检查同表活跃任务；请求当前actor/session、owner/host/Incus名/backup归属、host队列上限均未完整绑定到同一事务。
- `restoreTaskWorker.ts`领取只复核实例未deleted；执行与rollback按名称找到实例，未持久保存原实例和临时实例的UUID。原名称被复用后不能据名称存在决定删除临时副本。
- stop失败被吞掉；恢复临时实例后立即清理原备份/快照并删除原实例，没有完整临时实例身份、磁盘与网络可用验证。恢复网络/配额/设备及一机一卖管理边界须独立核验。
- 清理旧资源根据运行时列表扫描，缺少原清单及逐阶段回执。旧原实例删除、重命名、启动、数据库落库各点中断都可能留下不同远端状态。
- 僵尸恢复任务只按时间置FAILED，其他操作据PENDING/PROCESSING判断忙；未知远端恢复状态会失去持久门禁。不可只把超时错误写到FAILED就宣称恢复结束。
- 手工rollback无共享实例锁、当前会话复核和持久attempt；未知临时副本归属、正在执行的Incus操作以及迟到执行结果都需先识别。
- 恢复状态查询/取消/回滚沿用实例权限早期快照；任务创建者可能是管理员或宿主owner，不能套用上传仅实例owner的规则。取消须在锁内重新验证当前权限和原任务对象，查询不能暴露已转移前旧owner的敏感目标信息。

## 下一阶段边界

1. 入队锁host→instance，实例/host行锁后锁相关账户，核对当前授权、原实例归属、host TLS身份和ready backup；固定backup ID/Incus名/创建时间、原实例ID/Incus名、host身份摘要、actor session、唯一临时名及备份/快照清单。队列上限与插入同锁，复用snapshot/proxy/transfer/upload门禁。管理员/宿主owner授权与实例owner须分别记录，不能混为task.userId。
2. 在任何远端写之前读原实例UUID、原设备与磁盘身份，持久化核验结果。建立任务阶段、attempt UUID、当前远端operation与明确错误。每一步重读任务原绑定，不能以当前DB内容替换原意图。
3. 先持久记录恢复操作意图和唯一临时名，再恢复临时实例；保存并确认远端operation及临时UUID、原备份关系和目标存储池。超时/网络未知先查询原operation及固定临时实例，不重复POST创建，也不自动清理未知身份副本。
4. 删除原实例前必须确认原UUID不变、临时副本身份与恢复结果可靠、旧原实例确实停止，并按原网络/磁盘验收方案确认接替条件。禁止吞stop异常、仅看任务进度或HTTP成功便删除原数据。
5. 每个远端写后确认实际状态，再CAS推进持久阶段。重命名后原名必须是已保存的临时UUID，不能将任意同名实例当作恢复成功。原清单删除需确认对象身份，不能在重试时重扫并清除新资源。
6. 未决恢复继续阻断转移、重装、销毁、上传/备份和自动策略；门禁应覆盖所有相关数据库和worker入口。人工处理的FAILED记录也不能悄悄释放未知远端状态的门禁。用户取消只能在尚未开始远端操作时完成。
7. rollback同样作为持久操作。先确认当前actor/session及固定原/临时UUID、当前operation已结束，再决定启动原副本或继续恢复；无法确认原副本可靠时保留临时副本。旧副本不能被名称复用/旧任务迟到回执误删。

实现时可参考`services/transfer-cleanup.ts`的固定清单、UUID、阶段CAS与短事务远端确认结构，但不得直接照搬转移的资源删除范围。恢复是主动替换客机磁盘的独立操作，owner的主控OSS灾备目标仍禁止因面板恢复重建客户磁盘。既有`withSnapshotMutation`会把当前restore task自身当忙，恢复worker需要明确排除自身的专用门禁，不能整体跳过任务检查。

## 必需证据

- 真实PG/Fastify和mTLS边界：入队/领取/每个远端阶段的禁用/注销/owner/host/backup变化；任务同实例及host竞争、取消/rollback/删除交错。
- SIGKILL矩阵：原UUID落库前后、POST受理但未收回执、恢复完成但DB失败、原删除前后、临时重命名前后、启动与最终落库前后。重启只恢复同一意图，唯一剩余副本保护。
- 原身份被替换、403/超时/404、不完整恢复、临时名抢占、错误UUID、旧operation迟到、恢复时备份被删除、阶段CAS失败；失败不扩大远端删除范围。
- 真实Incus容器/VM、存储池、备份内容、原双栈设备/NAT/客户SSH身份及库存账目审计。边界替身与实机证据分别记录。

三台专用测试机资料继续按OWNER_REQUIREMENTS中的仓库外路径读取；当前SSH可信身份尚未闭合，不在此文复制连接凭据或将握手扫描当作认证证据。
